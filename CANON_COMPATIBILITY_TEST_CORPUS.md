## 1. Empirical Execution of `CAP3RDN.dll` in an Isolated WoW64 Harness

To objectively test whether Canon's original Host Rendering Engine (`CAP3RDN.dll`) can be executed independently, a 32-bit test harness (`scripts/test_hre_execute.ps1`) was constructed and executed under Windows WOW64 (`C:\Windows\SysWOW64\WindowsPowerShell\v1.0\powershell.exe`).

### 1.2 Root Cause of the Access Violation in `uiHREExecute`
Disassembly of `uiHREExecute` and its internal encoding routine `sub_53B6` reveals why isolated execution fails:
1. **Multi-Level Pointer Chaining:**
   Inside `sub_53B6`, the code executes:
   ```assembly
   mov  edx, [esp + 0x38]       ; Arg 2 (lpIn)
   mov  eax, [edx + 0x04]       ; First level dereference
   mov  eax, [eax + 0x04]       ; Second level dereference!
   mov  cl,  [eax + 0x07]       ; Read driver state flag
   mov  ch,  [eax + 0x06]       ; Read render resolution flag
   ```
2. **Coupling to Windows GDI Subsystem:**
   In the vendor driver architecture, `CAP3RDN.dll` is never called directly by user-space applications. It is called exclusively by `CAP3K.dll` (the GDI graphics driver). The `lpIn` structure is not a flat bitmap descriptor; it is an internal GDI `SURFOBJ` / `PDEV` / `HRE_DEV` context structure initialized during `DrvEnableSurface` and `DrvStartPage`.
3. **Conclusion on Isolated Execution:**
   `CAP3RDN.dll` **cannot** be executed in complete isolation without emulating the entire Windows XP 32-bit GDI graphics driver subsystem.
   > [!IMPORTANT]
   > We do **NOT** claim binary bit-exact equivalence with Canon's original output based solely on isolated execution of `CAP3RDN.dll`. True interoperability is proven by grammar compliance, lossless digital twin roundtrips, and empirical physical acceptance by the printer's Formatter ASIC.

## 3. SCoA Wire Grammar & Compliance Invariants

Every SCoA stream generated by `src/scoa.rs` strictly adheres to the hard requirements of the Canon Formatter ASIC (`IC1`):

1. **Initial Reference Scanline:** Line 0 is evaluated against an implicit 592-byte zero vector (`0x00`).
2. **Chunk Framing:** Compressed bytes are divided into packets of $\le 4,096$ bytes with opcode `0xC0A0` (total packet size $\le 4,100$ bytes). No token is split across packet boundaries.
3. **End-of-Page Termination (`OP_EOP` 0x42):** The final byte of the compressed stream must be `0x42`, signalling the decompressor to close its gate and trigger the paper pickup mechanism.
4. **16-Bit Word Alignment Padding:** If the total byte count of the compressed stream is odd, exactly one null byte (`0x00`) is appended.
